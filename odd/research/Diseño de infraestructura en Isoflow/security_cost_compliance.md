# Security threat modeling, policy validation, cost estimation, and compliance for infra design diagrams

## Threat modeling on diagrams (DFDs, trust boundaries, STRIDE per element/interaction) — which tools and what model attributes they require

### Takeaway
Model-driven threat modeling tools (Threagile, pytm, OWASP Threat Dragon, Microsoft Threat Modeling Tool, IriusRisk) all converge on the same underlying data model: components/assets with a security classification and a network-exposure flag, connected by data flows that carry a data classification and encryption/auth state, grouped inside trust boundaries/zones — from which STRIDE threats are derived either per-element or per-interaction. A diagram tool wanting this capability should persist these attributes on nodes and edges and either embed a rule engine or export to one of these formats.

### Cited Findings
- Threagile lets teams "model an architecture with its assets in an agile declarative fashion as a YAML file," then runs built-in and custom risk rules against that model to auto-generate a STRIDE-categorized risk report, a data-flow diagram, and JSON/Excel exports — positioned for CI/CD "threat-model-as-code" use. — [Threagile — Agile Threat Modeling Toolkit](https://threagile.io/)
- Threagile's model is organized around `technical_assets` (the primary analysis entry point), which link via `communication_links` and declare `data_assets_processed` / `data_assets_stored`; communication links themselves carry `data_assets_sent` / `data_assets_stored`; assets and links can be grouped via `trust_boundaries` and `shared_runtime`. Analysis runs in "analyze mode" applying risk-rule algorithms, and findings are tracked in a `risk_tracking` field. — [Threagile model docs](https://github.com/threagile/threagile/blob/master/docs/model.md)
- Threagile is written in Go, supports Docker deployment, a REST API server mode, and plugin-based custom rule injection; the risk rules are themselves expressible as custom YAML-based scripts. — [Threat Modeling as Code: Running Threagile on Every Architecture Change](https://www.michaelosburn.com/2026/06/08/threat-modeling-as-code-threagile-ci/)
- pytm (OWASP) is a Pythonic framework — the system model is defined in Python code (no GUI diagram editor) using elements: `TM`, `Element`, `Server`, `ExternalEntity`, `Datastore`, `Actor`, `Process`, `SetOfProcesses`, `Dataflow`, `Boundary`, `Lambda`, `LLM`, `Agent`. From the model it generates a Data Flow Diagram, a Sequence Diagram, and a threat list. — [GitHub - OWASP/pytm](https://github.com/OWASP/pytm); [Tool for Threat Modelling: PYTM](https://medium.com/@manoj-sharma-sec/tool-for-threat-modelling-pytm-ab8a2273f945)
- pytm's `Data` objects expose per-flow-endpoint encryption flags (`isSourceEncryptedAtRest`, `isDestEncryptedAtRest`) and a `Classification` enum for data sensitivity; a `TLSVersion` enumeration governs encryption-in-transit requirements on data flows. — [Threat modeling as code: exploring pytm](https://medium.com/@maciej.galeja/threat-modeling-as-code-exploring-pytm-550368de8070)
- OWASP Threat Dragon models are JSON files arranged around diagram-editor elements: metadata (title, owner, description, id), a `detail` section with `contributors`, and a `diagrams` array where each diagram has `title`, `thumbnail`, `diagramType` (e.g. `"STRIDE"`), `id`, and a `diagramJson.cells` array of typed diagram elements (e.g. `tm.Store`) with size/position. v1.x uses the JointJS graph format, v2.x uses AntV/X6 — the two are incompatible. Threat Dragon intends to migrate to the Threat Model Bill of Materials (TM-BOM) schema in v3.x. — [Schema | Threat Dragon docs](https://www.threatdragon.com/docs/development/schema.html); [OWASP/threat-dragon demo model](https://github.com/OWASP/threat-dragon/blob/main/ThreatDragonModels/demo-threat-model.json)
- The general model-as-code pattern (shared by Threat Dragon, pytm, Threagile) stores the threat model as JSON/YAML in the repo, so diagram and threat-list changes go through pull-request review like any other code change. — [Threat Modeling with STRIDE and DREAD (search synthesis)](https://inventivehq.com/blog/threat-modeling-stride-dread-complete-guide)
- Microsoft Threat Modeling Tool (part of the Security Development Lifecycle) implements "STRIDE-per-interaction" (from Adam Shostack's work) — threats are analyzed along the *connections* between elements rather than on individual elements, taking into account what data flows over each connection. Users draw a DFD with a component catalog and explicitly mark trust boundaries as dotted red lines; the tool then auto-generates a threat list per interaction. — [Getting Started - Microsoft Threat Modeling Tool - Azure | Microsoft Learn](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-getting-started); [Microsoft Threat Modeling Tool — STRIDE — Usage and Examples](https://medium.com/@hexshubz/microsoft-threat-modeling-tool-stride-usage-and-examples-bac88bde43eb)
- IriusRisk models architectures as a DFD (built on an embedded draw.io editor) organized around **trust zones** ("the different areas within which components are located... define how trustworthy an area is, based on how accessible it is: the more accessible, the less trustworthy"), **data flows** ("describe the movement of relevant information (assets) across our architecture"), and a library of **risk patterns** matched automatically against diagram elements plus per-component questionnaires and data-asset tags on flows, to auto-generate threats, weaknesses, and countermeasures. — [Threat Modeling Terminology](https://www.iriusrisk.com/resources-blog/threat-modeling-terminology); [IriusRisk: Create a diagram from scratch](https://www.iriusrisk.com/documentation/create-a-diagram-from-scratch)
- IriusRisk also maintains an open, platform-independent format for exchange: the Open Threat Model (OTM) standard. — [Introduction to the Open Threat Model standard](https://www.iriusrisk.com/resources-blog/introduction-to-the-open-threat-model-standard); [GitHub - iriusrisk/OpenThreatModel](https://github.com/iriusrisk/OpenThreatModel)

### Inferences
- A diagram tool aiming to support automated threat modeling should, at minimum, persist on every node: an internet-facing/exposure flag, a machine/technology type, and a set of processed/stored data-asset references; on every data asset: a confidentiality/sensitivity classification; on every edge (data flow): source/destination, protocol, authentication mechanism, and encryption-in-transit state; and should let the user draw explicit trust-boundary containers grouping nodes. This is the common denominator across Threagile, pytm, Threat Dragon, MTMT, and IriusRisk.
- Exporting to (or importing) Threagile YAML, pytm Python, Threat Dragon JSON, or IriusRisk's OTM format would let a diagram tool delegate the actual STRIDE rule evaluation to an existing engine rather than reimplementing threat rules from scratch — "model as code" interchange is a realistic integration point.
- STRIDE-per-interaction (MTMT-style) is more granular / diagram-native than per-element STRIDE, and maps naturally onto a diagram tool's edges (data flows) — likely the better default for a diagram-first product, supplemented with per-element checks (e.g. exposure, missing encryption) similar to Threagile/pytm/IriusRisk.

### Gaps
- I could not retrieve the full enumerated attribute list for Threagile's `technical_assets` and `data_assets` YAML schema (e.g., exact confidentiality/integrity/availability rating scales, encryption enum values, authentication enum values, `internet` boolean, `usage` field) — the fetched `docs/model.md` and landing page only describe the model's structural linking fields (`communication_links`, `data_assets_processed/stored`, `trust_boundaries`), not the full attribute/enum catalog. Direct inspection of the Threagile GitHub repo's schema file or example `threagile.yaml` would be needed to confirm exact field names and value sets before designing an equivalent data model.
- I did not verify pytm's complete `Element`/`Dataflow` attribute list (e.g., explicit `authenticatesDestination`, `authenticationScheme`, `protocol` fields) beyond the classification/encryption fields found.
- I did not find primary-source detail on IriusRisk's exact data-asset tagging schema (e.g., specific sensitivity levels) or its full risk-pattern rule catalog.

## Architecture rules/lint: policy-as-code applied to design models (OPA/Rego, Checkov/tfsec/Trivy-style rules)

### Takeaway
Policy-as-code engines like OPA/Rego and Checkov already express exactly the kind of design-time rules a diagram tool would want (public exposure, missing encryption, missing tags/owner, open ingress) against structured infrastructure data (IaC or JSON/HCL plans) — the same rule patterns can be re-targeted at a diagram's underlying JSON/graph model instead of a Terraform plan, since both are structured data that Rego/Checkov's engines can evaluate.

### Cited Findings
- OPA "is purpose built for policy evaluation and uses its declarative language Rego to reason about structured data like API requests, infrastructure-as-code files, and configuration data." It commonly runs "as a pre-deployment gate in CI/CD pipelines to evaluate infrastructure-as-code changes such as Terraform plans before deployment," with example policies that "reject risky infrastructure changes before they reach production, such as public network exposure or unsafe IAM changes." — [Open Policy Agent (OPA) docs](https://www.openpolicyagent.org/docs); [What is Open Policy Agent? — Orca Security](https://orca.security/resources/blog/what-is-open-policy-agent/)
- Rego is declarative: "policy authors can focus on what queries should return rather than how queries should be executed," and OPA use cases span Kubernetes admission control and Terraform policy enforcement, plus general CI/CD security/compliance gating. — [Open Policy Agent (OPA) Rego Language Tutorial](https://spacelift.io/blog/open-policy-agent-rego)
- Checkov ships with a large built-in check catalog and supports two custom-policy authoring modes: YAML custom policies (attribute blocks, connection blocks, logical operators `and`/`or`/`not` over resource attributes) and Python custom policies. — [YAML Custom Policies - checkov](https://www.checkov.io/3.Custom%20Policies/YAML%20Custom%20Policies.html); [Python Custom Policies - checkov](https://www.checkov.io/3.Custom%20Policies/Python%20Custom%20Policies.html)
- Concrete Checkov rule examples matching common "design-time" concerns: an S3 encryption check reads the `server_side_encryption_configuration` block and verifies AES-256 or `aws:kms` is configured; a public-access check flags "S3 Bucket has an ACL defined which allows public access"; a security-group example policy checks `aws_security_group` ingress `cidr_blocks` to fail when they contain `0.0.0.0/0` (using Rego/YAML `not` operator patterns). — [Checkov Quick Start](https://www.checkov.io/1.Welcome/Quick%20Start.html); [Custom YAML Policies Examples - checkov](https://www.checkov.io/3.Custom%20Policies/Examples.html)
- Checkov custom policies can also encode organizational tagging requirements, e.g. mandatory `Environment`, `Owner`, `Project`, `CostCenter` tags, alongside approved-encryption-algorithm and logging-mandate checks. — [Checkov Custom Policies (search synthesis)](https://www.checkov.io/3.Custom%20Policies/YAML%20Custom%20Policies.html)
- Checkov's built-in checks are mapped to compliance frameworks: "750+ built-in checks mapped to CIS benchmarks, NIST, HIPAA, PCI DSS, and SOC 2," reinforcing that the same rule-to-control mapping pattern used for IaC linting could tag diagram-model rule violations with compliance-framework references. — [Compliance framework mapping (search synthesis)](https://www.cisecurity.org/cybersecurity-tools/mapping-compliance/mapping-and-compliance-with-the-cis-controls)

### Inferences
- A diagram tool could implement "architecture lint" either by (a) embedding a small declarative rule engine (Rego-like, or a simpler YAML attribute-matcher like Checkov's custom-policy format) evaluated directly against its own node/edge JSON graph, or (b) exporting to Terraform-plan-shaped JSON / HCL and reusing Checkov/OPA/tfsec/Trivy unmodified as an external linting step. Given the diagram model won't naturally look like a Terraform plan, option (a) — a native rule engine over the diagram's own schema, with rules expressed in a Rego-inspired or Checkov-YAML-inspired syntax — is architecturally simpler for a design-time (pre-IaC) tool.
- Design-time rules a diagram tool should ship out of the box, drawing directly from the Checkov/OPA examples found: public database/storage exposure, missing encryption at rest/in transit, single-AZ (no redundancy) placement, missing backup/DR configuration, ingress rules open to `0.0.0.0/0`, and missing owner/cost-center/environment tags.

### Gaps
- I did not find a source describing a Checkov (or tfsec/Trivy) rule specifically for "single AZ" / missing multi-AZ redundancy — this is inferred from Well-Architected reliability guidance (see the reliability section below) rather than confirmed as an existing Checkov check ID. A rule with this exact intent should be verified against Checkov's current check catalog (e.g. searching for RDS/ASG multi-AZ check IDs) before citing a specific check ID.
- I did not verify whether tfsec or Trivy (as opposed to Checkov) publish the same public-exposure/encryption/tagging rule categories; the research focused on Checkov and OPA/Rego per the assignment's primary examples.

## Cost estimation at design time (Cloudcraft, Infracost, cloud pricing APIs) — what node properties are needed

### Takeaway
Design-time cost estimation is well precedented — Cloudcraft prices AWS/Azure diagrams live, and Infracost prices Terraform plans by resolving resource attributes (instance type, storage size, replication/HA settings) against synced pricing databases; all three major clouds expose programmatic list-price APIs (AWS Price List Query API, Azure Retail Prices API, GCP Cloud Billing Catalog API) that a diagram tool could query directly given the same resource attributes.

### Cited Findings
- Infracost is "a cloud cost estimation tool for Terraform that shows infrastructure cost breakdowns and diffs directly in pull requests," and separately "provides an API for programmatic access to cloud pricing data and cost estimates." — [GitHub - api-evangelist/infracost](https://github.com/api-evangelist/infracost)
- Infracost's Cloud Pricing API is "a GraphQL-based API that includes all public prices from AWS, Azure, and Google," with prices "updated on a weekly job," and totals "3M prices from AWS, Azure and GCP." — [Cloud Pricing API | Infracost docs](https://www.infracost.io/docs/supported_resources/cloud_pricing_api/); [Cloud Pricing API: 3M prices from AWS, Azure and GCP - Infracost](https://www.infracost.io/blog/cloud-pricing-api/)
- Infracost's estimation flow: it runs `terraform init`/`terraform plan` internally to generate a plan JSON, reads "resource types, instance types, storage sizes, replication settings, and other cost-relevant attributes from the plan output," then queries its pricing database (synced from AWS/GCP/Azure price lists) "to find the on-demand price for each resource configuration." — [COST ESTIMATION FOR INFRASTRUCTURE (search synthesis)](https://medium.com/devops-dudes/cost-estimation-for-infrastructure-8bd8a2d49d2f)
- A third-party tool (InfraSketch) demonstrates the diagram-integration pattern directly: "paste your configuration to generate an architecture diagram, then overlay the Infracost JSON output to see per-resource cost annotations directly on the diagram." — [Cloud Cost Estimation with Infracost: How It Works and What It Covers](https://dev.to/pandey-raghvendra/visualize-infracost-on-your-architecture-diagram-1fmg)
- Cloudcraft "calculates the estimated AWS or Azure spend for your architecture blueprint, so you can forecast costs before you deploy," provides "cost visibility at a resource- and aggregate-level" and "dynamically updates cost estimates as you iterate," with daily/weekly/monthly projection options (Cloudcraft Budget). It can also import a live AWS/Azure account into an isometric diagram automatically, and separately supports AWS, Azure, GCP, Oracle Cloud, and on-prem VMware vSphere diagrams. — [Cloudcraft – Live AWS, Azure & GCP Architecture Diagrams](https://www.cloudcraft.co/); [Plan new architectures and track your cloud footprint with Cloudcraft by Datadog](https://www.datadoghq.com/blog/cloud-architecture-diagrams-cost-compliance-cloudcraft-datadog/)
- AWS Price List Query API: "programmatically query AWS for services, products, and pricing information," "uses product attributes and provides prices at the SKU level," usable to "build cost control and scenario planning tools, reconcile billing data, forecast future spend for budgeting purposes, and provide cost benefit analyses." — [Finding services and products using AWS Price List Query API](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/using-price-list-query-api.html)
- GCP Cloud Billing Catalog API provides "programmatic, real-time access to authoritative Google Cloud Platform (GCP) list pricing," mirroring what's shown for GCP SKUs on the public pricing site. — [Introducing Cloud Billing Catalog API](https://cloud.google.com/blog/topics/cost-management/introducing-cloud-billing-catalog-api-gcp-pricing-in-real-time)
- Azure Retail Prices API: unlike the web-based Pricing Calculator, "the API enables automated pricing lookups, bulk exports, and integration with custom cost estimation tools." — [Azure Retail Prices API: Python & PowerShell Code Examples](https://inventivehq.com/knowledge-base/microsoft-azure/how-to-export-azure-pricing-data-for-skus-and-services)

### Inferences
- To price a diagram node, a design tool needs at minimum: cloud provider, region, resource/service type (e.g. EC2/VM/Cloud SQL), instance/SKU size or tier, storage amount (GB) and storage class, and — for usage-based resources — expected request volume/data-transfer volume; replication/HA settings (e.g. Multi-AZ) also change price and should be modeled as a first-class node property since Infracost explicitly reads "replication settings" from Terraform plans.
- Given three independent, free, programmatic pricing APIs exist (AWS Price List Query API, Azure Retail Prices API, GCP Cloud Billing Catalog API) alongside Infracost's own aggregating GraphQL API (3M SKUs, weekly refresh, paid product), a diagram tool has a real build-vs-buy choice: query the three provider APIs directly (free, more integration work, still needs a synced local cache for latency) versus integrating Infracost's Cloud Pricing API (single interface, and diagram-node attributes map closely to what Infracost already expects to read off a Terraform plan).

### Gaps
- Exact Infracost Cloud Pricing API authentication/access terms (whether the GraphQL Cloud Pricing API is available standalone vs. bundled only with the paid Infracost Cloud product) were not confirmed beyond the "$1,000/month base, 10 seats" figure found for Infracost Cloud — unclear if that price gates the pricing API itself or only the full SaaS product; needs direct pricing-page verification.
- I did not confirm current AWS Price List API and Azure Retail Prices API rate limits, auth requirements (AWS requires signed requests; Azure Retail Prices API is unauthenticated/public), or response latency characteristics suitable for real-time diagram cost updates — would need to consult the official API reference docs directly.

## Compliance mapping (CIS, SOC 2, ISO 27001, PCI DSS, HIPAA) — how design tools tag components/flows with controls; data residency/region constraints

### Takeaway
No source found describes a diagram-first design tool that natively tags components with compliance controls; the established pattern instead comes from IaC scanners (Checkov) and GRC platforms that map a shared control set once across multiple frameworks (SOC 2, ISO 27001, PCI DSS, CIS, NIST, HIPAA) and treat automated evidence (config scans, access reviews, change records) as proof — a diagram tool would need to adopt the same "map controls once, tag components with controls, auto-generate evidence" model rather than inventing framework-specific tags.

### Cited Findings
- "Organizations rarely operate under a single compliance framework today" and "these frameworks share significant overlap" — the most effective approach is to "manage controls instead of frameworks: establish a common set of controls and map each control to applicable requirements" once. — [How to Map Controls Across Multiple Compliance Frameworks (ISO 27001, PCI DSS, GDPR)](https://www.cybersierra.co/blog/streamline-compliance-controls)
- The Open Security Architecture (OSA) controls set maps to ISO 27001, COBIT, CIS Controls, NIST CSF, and SOC 2; CIS Controls v8.1 has an explicit mapping to PCI DSS v4.0. — [Framework Mappings | Open Security Architecture](https://opensecurityarchitecture.org/frameworks/); [Mapping and Compliance with the CIS Controls](https://www.cisecurity.org/cybersecurity-tools/mapping-compliance/mapping-and-compliance-with-the-cis-controls)
- "The point of mapping is that each row produces evidence automatically when the control is real" — e.g., IAM Identity Center emits access reviews, pipelines emit change records, and a config service emits drift detection as evidence for a mapped control. — [AWS Compliance Controls Mapping: Services to SOC 2, PCI DSS & ISO 27001](https://dev.to/sahil_dubey_c4ed5879c7eaa/aws-compliance-controls-mapping-security-devops-compliance-mapping-services-to-soc-2-pci-dss--5dk2)
- Checkov "ships with 750+ built-in checks mapped to CIS benchmarks, NIST, HIPAA, PCI DSS, and SOC 2" — i.e., individual IaC-linting rules are tagged with the compliance frameworks/controls they satisfy, which is the closest confirmed precedent for "tag a design element/rule with a compliance control." — [Compliance framework mapping (search synthesis, sourced via CIS mapping article)](https://www.cisecurity.org/cybersecurity-tools/mapping-compliance/mapping-and-compliance-with-the-cis-controls)
- Multi-framework GRC platforms (e.g., Quantarra, cited in search) let organizations "manage multiple frameworks through a unified control architecture, mapping controls across SOC 2, ISO 27001, PCI DSS, NIST CSF, and custom frameworks while automating processes" — evidence this "unified control graph" pattern is the industry-standard approach outside of IaC scanners too. — [How to Map SOC 2, ISO 27001, PCI DSS, and NIST Controls in One Platform](https://quantarra.io/blog/how-to-map-soc-2-iso-27001-pci-dss-and-nist-controls-in-one-platform)

### Inferences
- A diagram tool's compliance feature should be built as: (1) one internal canonical control set, (2) a mapping table from each canonical control to the specific clauses/IDs in CIS, SOC 2, ISO 27001, PCI DSS, and HIPAA it satisfies, and (3) diagram-level rules (the same rules used for architecture lint, see above) that assert a control is met (e.g., "encryption at rest configured" -> satisfies control X -> which maps to PCI DSS Req 3.4, ISO 27001 A.8.24, SOC 2 CC6.1, etc.), rather than tagging each diagram node independently per framework.
- Data residency/region constraints were not directly evidenced in search results for any design tool, but they compose naturally onto this same model as a component-level attribute (allowed/required region(s)) checked by an architecture-lint rule (e.g., "PII data asset stored in an EU-only trust boundary must reside in an eu-* region").

### Gaps
- No primary source was found for a diagram/design tool (Cloudcraft, IriusRisk, Threagile, or others) that natively exposes compliance-framework tagging in its UI or model schema; this entire section is inferred from IaC-scanner (Checkov) and GRC-platform patterns, not from a diagram-tool-specific implementation. This should be flagged to the report writer as an evidence gap — direct product documentation (e.g., Cloudcraft's "compliance" features referenced in a Datadog blog title) was not fetched in full and should be checked before asserting Cloudcraft has this capability.
- No source specifically addressed how any tool represents data-residency/region constraints as a first-class diagram attribute or validation rule; this is inferred, not confirmed.
- HIPAA-specific control mapping detail (as distinct from the general SOC2/ISO27001/PCI DSS/CIS overlap discussion) was not found beyond the general claim that Checkov's check catalog includes HIPAA-mapped checks.

## Reliability/DR annotations (SLO, RTO/RPO, redundancy, backup) — how design tools represent and check them

### Takeaway
RTO/RPO and multi-AZ/backup are well-defined, standard cloud-reliability concepts (documented authoritatively by AWS and Azure Well-Architected guidance) that a diagram tool can attach as per-component or per-system attributes and validate with lint-style rules, but no source in this research described an existing diagram tool that natively captures and checks RTO/RPO/SLO annotations on the diagram itself — this is an inferred capability, not a confirmed existing feature of any named tool.

### Cited Findings
- "RTO defines how quickly a system must be restored after a disruption and represents the organization's tolerance for downtime. RPO defines how much data loss is acceptable and reflects how frequently data must be backed up." — [RPO and RTO · A Guide to Software Architecture](https://raghumb.gitbooks.io/a-guide-to-software-architecture/content/infrastructure_concepts/rto_and_rtp.html)
- "Synchronous replication ensures zero data loss (RPO=0) but is limited by the speed of light, making it suitable only for multi-AZ setups," and "a Multi-AZ DR strategy within an AWS Region can provide protection against localized disruptions like power outages and flooding." — [AWS Disaster Recovery 2026: Strategy, Backup & Cyber Resilience Guide](https://www.rubrik.com/insights/aws-disaster-recovery-strategy-guide)
- AWS documents four primary DR strategies (backup & restore, pilot light, warm standby, multi-site active/active) that "scale in cost and complexity based on your RPO and RTO requirements," with differing RTO/RPO/cost trade-offs per strategy. — [Reliability Pillar - AWS Well-Architected Framework](https://docs.aws.amazon.com/pdfs/wellarchitected/latest/reliability-pillar/wellarchitected-reliability-pillar.pdf); [Disaster Recovery (DR) Architecture on AWS, Part I](https://aws.amazon.com/blogs/architecture/disaster-recovery-dr-architecture-on-aws-part-i-strategies-for-recovery-in-the-cloud/)
- Azure's Well-Architected Framework provides equivalent DR design guidance for multi-region deployments, and a related practical guide frames "Resilience Targets: RTO and RPO" as first-class design inputs. — [Develop a disaster recovery plan for multi-region deployments - Azure Well-Architected](https://learn.microsoft.com/en-us/azure/well-architected/design-guides/disaster-recovery); [Resilience Targets: RTO and RPO - Azure Architecture Practical Guide](https://yeongseon.dev/azure-architecture-practical-guide/reference/resilience-targets-rto-rpo/)
- Recommended DR lifecycle management practice includes "testing backups, exercising restore procedures, validating standby environments, reviewing RTO and RPO, checking ownership, and updating automation after architectural changes" — implying RTO/RPO values should be tracked as living metadata tied to specific components, not just narrative documentation. — [Disaster Recovery in Cloud Environments: RTO, RPO, Backups, and Multi-Region Design](https://www.examsnap.com/certification/disaster-recovery-in-cloud-environments-rto-rpo-backups-and-multi-region-design/)
- Modern DR practice increasingly uses "Infrastructure as Code with tools like Terraform or AWS CloudFormation, enabling engineers to version-control their entire DR environment" — reinforcing that DR/redundancy configuration is expressible as structured, checkable resource attributes (matching the "single-AZ vs multi-AZ" lint-rule pattern from the policy-as-code section above). — [Architecting Cloud Based DR](https://medium.com/@frankd228801/architecting-cloud-based-dr-520784ae4bfd)

### Inferences
- A diagram tool should model RTO/RPO and redundancy as attributes at the level of a logical "system"/"service" grouping (not just a single node), since DR strategy (backup & restore vs. pilot light vs. warm standby vs. multi-site active/active) is inherently a multi-component pattern — e.g., a redundancy/AZ-count attribute per compute/database node, plus a target RTO/RPO value and backup-frequency attribute per data asset or service group, checked by lint rules like "production data asset with RPO < 1h must have synchronous/multi-AZ replication enabled" or "internet-facing production service must span >= 2 AZs."
- SLO is a related but distinct concept (availability/latency/error-budget targets, not directly evidenced in the search results) that would need separate research if the report needs SLO-specific tooling precedent; treat as a gap below.

### Gaps
- No source described an existing diagram/design tool (Cloudcraft, IriusRisk, Threagile, Lucidchart, etc.) with native RTO/RPO/SLO annotation fields or automated redundancy checks — the recommendation above is synthesized from general cloud-reliability best-practice documentation (AWS/Azure Well-Architected), not from a design-tool implementation. This should be presented to the report writer as a design opportunity/gap in the current tooling landscape rather than a confirmed existing pattern.
- SLO (service-level objective) representation and tooling was not directly researched — only RTO/RPO/redundancy/backup were covered per the assigned key question wording ("SLO, RTO/RPO, redundancy... backup"); a follow-up search specifically on "SLO annotation architecture diagram" or error-budget tooling would be needed to close this gap.
- Did not verify whether Checkov (or a similar scanner) has a confirmed, named check specifically enforcing "Multi-AZ enabled" (e.g., for RDS) — inferred as a plausible rule type from Well-Architected guidance and Infracost's mention of reading "replication settings," but not confirmed as an existing Checkov check ID.
