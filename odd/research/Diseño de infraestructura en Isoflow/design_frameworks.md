# Infrastructure/Architecture Design Framework Requirements for Diagramming Tools

## AWS Well-Architected Framework: what design information must be captured/reviewed, and what does the Well-Architected Tool / lenses / diagram guidance ask?

### Takeaway
The AWS Well-Architected Framework (WAF) is organized into six pillars — operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability — and the Well-Architected Tool operationalizes it as a per-workload questionnaire (with pluggable "lenses") that also captures workload metadata such as environment type, AWS/non-AWS regions, and linked account IDs. Separately, AWS's official diagram guidance (Architecture Icons + grouping conventions) expects diagrams to nest resources inside a strict containment hierarchy: AWS Cloud → Region → VPC → Availability Zone → Subnet → Security Group.

### Cited Findings
- The AWS Well-Architected Framework's six pillars are operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability; the framework states that neglecting them "can become challenging to build a system that delivers on your expectations and requirements" — [AWS Well-Architected Framework: Pillars](https://docs.aws.amazon.com/wellarchitected/latest/framework/the-pillars-of-the-framework.html)
- The AWS Well-Architected Tool evaluates a "workload" (defined as "the collection of resources and code that make up a cloud application") by having users answer questions across each pillar, and supports three question-set types: the core Framework, AWS-provided lenses (e.g., Serverless, HPC, IoT, SaaS), and user-created Custom Lenses (JSON-authored, with pillars, questions, choices, risk rules, and improvement plans) — [AWS Well-Architected Tool FAQs](https://aws.amazon.com/well-architected-tool/faqs/); [Custom Lenses announcement](https://aws.amazon.com/blogs/aws/well-architected-custom-lenses-internal-best-practices/)
- When defining a workload in the WA Tool, required/optional fields include: Name, Description, Review owner, **Environment** (Production or Pre-production), **AWS Regions** (multi-select) and **Non-AWS regions** (up to 5, free text), **Account IDs** (up to 100), an optional AppRegistry **Application** ARN, an optional **Architectural design** URL, **Industry type**/**Industry**, Trusted Advisor activation, Jira sync settings, and Tags. Up to 20 lenses can be applied per workload — [Defining a workload in AWS WA Tool](https://docs.aws.amazon.com/wellarchitected/latest/userguide/define-workload.html)
- AWS Reliability pillar defines Disaster Recovery (DR) objectives distinct from steady-state availability: **RTO** (Recovery Time Objective, the maximum acceptable delay before service restoration) and **RPO** (Recovery Point Objective, the maximum acceptable data loss window since the last recovery point), illustrated on a timeline relative to the disaster event — [AWS Reliability Pillar: DR objectives](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-objectives.html)
- AWS defines four DR strategies on a cost/complexity spectrum, each with distinct architectural signatures: **Backup and restore** (periodic/continuous backups of data + IaC-defined infrastructure/AMIs, redeployed on failover; suited to single-AZ or single-datacenter loss); **Pilot light** (continuous cross-region data replication + "switched-off" core infrastructure that must be turned on/scaled at failover; commonly implemented via AWS Elastic Disaster Recovery); **Warm standby** (a scaled-down but always-on, fully functional copy of production in a second Region, scaled up via Auto Scaling at failover — a "statically stable" fully-provisioned variant is called *hot standby*); and **Multi-site active/active** (workload runs simultaneously in multiple Regions and serves live traffic from all of them, with data-consistency strategies described as *write global*, *write local*, or *write partitioned*) — [AWS Whitepaper: Disaster Recovery Options in the Cloud](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html)
- AWS recommends using Infrastructure as Code (CloudFormation/CDK, including cross-account/cross-Region StackSets) to make DR redeployment predictable, and recommends using a separate AWS account per DR Region "to provide the highest level of resource and security isolation" — [AWS Whitepaper: DR Options](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html)
- AWS distinguishes *data plane* vs *control plane* operations for failover reliability, recommending failover automation rely on data-plane operations (e.g., Route 53 health-check on/off switches via Application Recovery Controller, or Global Accelerator traffic dials) because they have higher availability design goals than control-plane operations (e.g., ordinary DNS weighted-routing changes) — [AWS Whitepaper: DR Options](https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html)
- AWS Architecture Icons are published as an official, versioned icon set (quarterly-updated packages) intended for use in diagrams, whitepapers, presentations, datasheets, and posters, with an explicit instruction to check that icon libraries are current since "some libraries may contain legacy icon sets" — [AWS Architecture Icons](https://aws.amazon.com/architecture/icons/)
- The AWS Architecture Icons "Groups" library ships dedicated container/frame shapes — including AWS Cloud, Region, Virtual Private Cloud (VPC), Availability Zone/"availability group", VPC subnet, Security Group, Auto Scaling group, and corporate data center — each identified by a small icon in its upper-left corner, and diagrams are expected to nest these to reflect the real containment hierarchy (AWS Cloud → Region → VPC → Availability Zone → Subnet → Security Group), with redundant resources placed in each AZ boundary (e.g., labeled `us-east-1a`, `us-east-1b`) — [AWS diagram/icon groups — search synthesis, primary source AWS Architecture Icons asset packages](https://aws.amazon.com/architecture/icons/)
- General (secondary-source) AWS diagram best practice: show VPC boundaries and Availability Zones in essentially every non-fully-serverless diagram, use current official icons so reviewers can identify services instantly, group related resources for clarity, keep naming consistent, minimize clutter, and keep diagrams updated as systems evolve — [Diagrams.so: AWS Architecture Diagram Best Practices](https://diagrams.so/blog/aws-architecture-diagram-best-practices); [AWS Architecture Center](https://aws.amazon.com/architecture/)

### Inferences
- A diagramming/design tool aiming to satisfy AWS WAF review needs a **workload-level metadata model**, not just shapes: fields for environment (prod/pre-prod), one-or-more AWS Regions plus free-text non-AWS regions, linked account IDs, and an "architectural design URL" — i.e., the tool should be able to export a shareable link/reference that a WA Tool review can point to.
- To "show multi-AZ redundancy" the tool must model **nested containment groups** with fixed semantics — Account/Cloud → Region → VPC → Availability Zone → Subnet → Security Group — and must let users place multiple *replica* instances of the same logical resource inside sibling AZ containers (not just draw a box labeled "AZ"), so redundancy is structurally verifiable (e.g., "this RDS instance has a standby in a second AZ container").
- To represent AWS's four DR strategies distinctly, the tool needs to express **cross-region pairs** with an explicit relationship type carrying replication semantics (continuous async replication vs periodic backup vs active-active) and **resource state** (always-on vs scaled-down-standby vs deployed-but-off), plus a way to tag which Region is "active" vs "passive"/"DR".
- To capture RTO/RPO, the tool should support **attaching quantitative SLO-like properties** (RTO, RPO, availability target) to a workload or to individual data-bearing resources, since DR-strategy choice is explicitly driven by these numbers per AWS guidance.
- To be lens/pillar-review-ready, the tool would benefit from being able to **tag diagram elements or the whole workload with pillar-relevant properties** (e.g., a "Security" tag on a resource, a "Cost" tag, an "Industry type" workload property) that could later be exported into a WA-Tool-style checklist, though nothing in the sources indicates AWS ingests diagrams programmatically into the WA Tool — the "Architectural design" field is just a URL link, not a structured import.
- Using data-plane vs control-plane distinctions implies a tool could usefully let users annotate **which operations/paths are "data plane" (high-resilience) vs "control plane" (lower-resilience)** on failover-related connections, though this is a stretch beyond what current AWS diagram guidance explicitly asks for in a *diagram* (it's a DR-design consideration, not a documented AWS diagramming icon convention).

### Gaps
- AWS's official diagram-icon page itself (aws.amazon.com/architecture/icons/) does not, in the fetched content, spell out formal grouping/nesting rules — the group hierarchy (AWS Cloud → Region → VPC → AZ → Subnet → Security Group) is confirmed via a secondary-source search synthesis rather than a directly quoted primary-source passage; a follow-up fetch of the actual "AWS Architecture Icons Asset Package" guidelines PDF/pptx (not retrievable via WebFetch in this session — search results only listed SlideShare mirrors) would be needed to get AWS's own written grouping guidance verbatim.
- Could not confirm whether the AWS Well-Architected Tool ingests or validates architecture *diagrams* directly (vs. only a URL reference) — the "Architectural design" field appears to be a simple link, not a structured diagram import; no evidence found either way of diagram-based automated analysis.
- One fetch of `rel_planning_network_topology.html` (intended to source specific REL pillar network-topology best-practice text) returned content that could not be verified as directly quoted from the live AWS page rather than model-generalized filler; it is excluded from Cited Findings and only the confirmed page (`rel-08.html`, on change management) is cited for that pillar area. AWS's specific network-segmentation and fault-isolation best-practice IDs (e.g., exact REL10/REL11 wording) were not independently confirmed.

## Azure Well-Architected Framework and Google Cloud Architecture Framework: pillars and additional design considerations (landing zones, resource hierarchy)

### Takeaway
Azure's Well-Architected Framework has five pillars (reliability, security, cost optimization, operational excellence, performance efficiency) and is explicitly connected to, but not dependent on, Azure Landing Zones as the governed environment workloads are deployed into. Google Cloud's Well-Architected Framework has six pillars (operational excellence; security, privacy & compliance; reliability; cost optimization; performance optimization; sustainability) plus cross-pillar "perspectives," and separately prescribes a resource-hierarchy design (Organization → Folders → Projects) with named hierarchy patterns (environment-based, business-unit/region-based, accountability-framework-based).

### Cited Findings
- Azure Well-Architected Framework pillars and their core concern, per Microsoft's own matrix: **Reliability** (resiliency, availability, recovery), **Security** (data protection, threat detection/mitigation — protecting confidentiality, integrity, availability), **Cost Optimization** (cost modeling, budgets, reducing waste), **Operational Excellence** (holistic observability, DevOps practices), **Performance Efficiency** (scalability, load testing) — [Microsoft Learn: Azure Well-Architected Framework pillars](https://learn.microsoft.com/en-us/azure/well-architected/pillars)
- Microsoft provides an **Azure Well-Architected Review** assessment tool built on the five pillars, and **Azure Advisor** / **Azure Advisor score** analyze resource configuration and usage telemetry against the same pillars to generate prioritized recommendations — [Microsoft Learn: Azure Well-Architected Framework pillars](https://learn.microsoft.com/en-us/azure/well-architected/pillars)
- An Azure Landing Zone is described as a pre-configured, governed environment (networking, identity, governance, and security foundations already in place) into which workloads are deployed; the Well-Architected Framework "often references Azure landing zones, but it isn't dependent on a specific platform implementation" — [Nathan Nellans: Azure CAF, Landing Zones, and WAF](https://www.nathannellans.com/post/azure-cloud-adoption-framework-landing-zones-and-the-well-architected-framework); [Microsoft Learn: Expand your landing zone](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/)
- Google Cloud's Well-Architected Framework organizes guidance into six pillars — **Operational Excellence** (deploying, operating, monitoring, managing workloads; incident management, automation, continuous improvement), **Security, Privacy, and Compliance** (security-by-design, zero trust, shift-left security, responsible AI, regulatory alignment), **Reliability** (resilience/high availability defined against user goals, redundancy, horizontal scalability, observability, graceful degradation, failure testing/postmortems), **Cost Optimization** (aligning spend with business value, cost awareness), **Performance Optimization** (resource allocation, elasticity, modular design, continuous monitoring), and **Sustainability** (low-carbon regions, energy-efficient ML, resource optimization) — plus cross-pillar "perspectives" for domains like AI/ML and Financial Services — [Google Cloud Well-Architected Framework](https://docs.cloud.google.com/architecture/framework)
- Google Cloud's recommended resource hierarchy has three levels: **Organization** (single root node recommended "except for in specific situations"), **Folders** (intermediate containers that inherit and can override policy from parents), and **Projects** (the operational unit where resources actually live); IAM allow-policies are additive while deny-policies restrict, and organizations should document policy inheritance, compliance/regulatory needs per folder, and operational ownership per level — [Google Cloud: Decide a resource hierarchy for your Google Cloud landing zone](https://docs.cloud.google.com/architecture/landing-zones/decide-resource-hierarchy)
- Google names three concrete hierarchy patterns: an **environment-based hierarchy** (folders for dev/test/prod with environment-specific policy), a **business-unit or region-based hierarchy** (folders per subsidiary/geography/legal entity with distinct governance), and an **accountability-framework hierarchy** (folders per product team/independent workload); best practice explicitly warns against mapping corporate org charts directly onto the resource hierarchy, favoring operational needs instead, and recommends keeping bootstrap/shared-services resources in dedicated folders — [Google Cloud: Decide a resource hierarchy](https://docs.cloud.google.com/architecture/landing-zones/decide-resource-hierarchy)

### Inferences
- Because both Azure and GCP explicitly separate the **pillar-based quality framework** from a **landing-zone/resource-hierarchy governance layer**, a diagramming tool targeting multi-cloud infra design needs at least two independent modeling axes: (1) a *governance/organization containment hierarchy* (Azure Management Group → Subscription → Resource Group; GCP Organization → Folder → Project) distinct from (2) the *network/AZ/region containment* used for redundancy — these are not the same nesting and both need first-class container types.
- To "show a landing zone" a tool needs container types for **Management Group** and **Subscription** (Azure) or **Organization**, **Folder**, and **Project** (GCP), each carrying policy/governance metadata (e.g., which policies apply), separate from VPC/VNet-level network containers.
- Since GCP explicitly warns against 1:1 mapping of org charts to folders, a design tool should let users label *why* a given folder/grouping exists (environment vs business-unit vs accountability) as metadata, to support review/documentation rather than only visual nesting.
- Azure's "not dependent on a specific platform implementation" stance suggests a tool need not force landing-zone-shaped diagrams for Azure resources, but should still support optional landing-zone containers for teams that use them.

### Gaps
- The fetched Google Cloud Architecture Framework overview page did not, in the retrieved content, give resource-hierarchy guidance directly (it was explicitly marked "not included"); that guidance was instead sourced from a separate, more specific landing-zone page. The overview page's list of "six pillars" partly diverges in naming from some secondary sources (e.g., "System Design" vs "Performance Optimization" as pillar names) — this discrepancy was not fully reconciled against Google's current canonical pillar list and should be treated as a minor naming-uncertainty gap.
- Azure Landing Zone architectural components (hub-spoke networking, management groups, policy assignment specifics) were not deeply researched beyond the definitional summary above; a dedicated Azure Landing Zone architecture page was not fetched in this pass.
- No Azure or GCP equivalent of AWS's official "Architecture Icons grouping" written guidance was located/fetched in this research pass (only inferred from general resource-hierarchy docs), so direct diagram-icon conventions for Azure/GCP remain a gap.

## C4 model (context, container, component, deployment) and Structurizr notation

### Takeaway
The C4 model defines four notation-independent abstraction levels (System Context, Container, Component, Code) for describing a software system's structure, plus a separate Deployment Diagram type that maps containers onto infrastructure via **deployment nodes** (nestable, representing physical/virtual/containerized infrastructure or execution environments) and **infrastructure nodes** (supporting elements like DNS, load balancers, firewalls); Structurizr implements this as a diagrams-as-code DSL where `deploymentEnvironment`, `deploymentNode`, and `containerInstance` blocks are nested to declare the same structures in text.

### Cited Findings
- The C4 model provides "a set of hierarchical diagrams: system context, containers, components, and code" — System Context shows the system and its relationships to external systems/users (broadest view, for all audiences); Container zooms into one system to show its major deployable/runnable units (applications, databases, microservices) and their interactions (technical audience); Component breaks a single container into its internal components (for architects/developers); Code is the most detailed level (classes/functions/modules, for developers) — [C4 model official site](https://c4model.com/)
- The model is explicitly "notation independent" and "tooling independent" — [C4 model official site](https://c4model.com/)
- A **deployment node** "represents where an instance of a software system/container is running; perhaps physical infrastructure (e.g. a physical server or device), virtualised infrastructure (e.g. IaaS, PaaS, a virtual machine), containerised infrastructure (e.g. a Docker container), an execution environment (e.g. a database server, Java EE web/application server, Microsoft IIS), etc." Deployment nodes can be nested inside one another — [C4 model: Deployment diagram](https://c4model.com/diagrams/deployment)
- **Infrastructure nodes** represent supporting/ancillary elements that facilitate deployment but aren't the primary focus — e.g., DNS services, load balancers, firewalls — [C4 model: Deployment diagram](https://c4model.com/diagrams/deployment)
- Structurizr's DSL expresses a deployment view as nested blocks: `deploymentEnvironment "Name" { deploymentNode "Node" { containerInstance containerName; deploymentNode "Nested Node" { containerInstance anotherContainer } } }`, and a corresponding view is declared with `deployment * environmentName { include *; autoLayout lr }` — deployment nodes nest hierarchically, and container instances are references to containers already defined in the (separate) container-level model — [Structurizr DSL Cookbook: Deployment view](https://docs.structurizr.com/dsl/cookbook/deployment-view/); [Structurizr: Deployment diagram help](https://structurizr.com/help/deployment-diagram)

### Inferences
- A diagramming tool that wants to be "C4-deployment-capable" needs at minimum three distinct element kinds beyond ordinary shapes: (1) **Deployment Node** (nestable, with a "technology"/infrastructure-type attribute — physical, virtual/IaaS, containerized, execution-environment), (2) **Infrastructure Node** (a non-primary supporting element type, e.g., DNS/load-balancer/firewall, visually distinguishable from deployment nodes), and (3) **Container/System instance** placement references that link back to a separate, higher-level (context/container) model of the software system — i.e., deployment diagrams should reference the same logical containers defined at the Container-diagram level rather than being drawn independently, to keep the levels consistent.
- Supporting "diagrams-as-code" (as Structurizr does) implies the tool's internal model should be serializable to/from a structured nested format (JSON/DSL) so that deployment nodes-within-nodes and container-instance placement can be version-controlled and regenerated — a capability distinct from pure freeform drawing.
- Relationships in C4 are expected to carry **technology labels** (e.g., "HTTPS/JSON", "JDBC") per general C4 practice; a tool should let connectors carry a technology/protocol label field, not just a generic line.
- Because C4 separates "abstraction level" (Context/Container/Component/Code) from "deployment" as an orthogonal concern, a tool ideally supports multiple *views* over one underlying model (the same system modeled once, several diagram types generated/filtered from it) rather than one diagram = one independent drawing — this mirrors Structurizr's "model once, view many times" architecture.

### Gaps
- The exact syntax for defining an **infrastructure node** in Structurizr DSL (as opposed to a deploymentNode) was not directly retrieved — the cookbook fetch only returned deploymentNode/containerInstance/deploymentEnvironment syntax, not an `infrastructureNode` example; this should be treated as an unconfirmed detail if precise DSL syntax is needed later.
- Did not verify the precise, official C4 relationship notation for technology labels (arrow syntax, whether labels are mandatory) from a primary source in this pass — the claim above is inferred from general C4 convention rather than a directly cited passage.

## arc42 (deployment view, crosscutting concepts) and ISO/IEC/IEEE 42010 (viewpoints/views/stakeholders/concerns)

### Takeaway
arc42's Section 7 (Deployment View) requires mapping software building blocks onto infrastructure elements (locations, environments, computers/processors, networks, topologies) across all relevant environments (dev/test/prod), while Section 8 (Crosscutting Concepts) documents cross-cutting technical/process topics (e.g., a "dynamic deployment concept") that the deployment view should reference. ISO/IEC/IEEE 42010 defines the standard conceptual vocabulary underpinning both: an Architecture Viewpoint frames one or more Stakeholder Concerns, and each Architecture View conforms to exactly one Viewpoint that specifies it; the 2nd edition adds "Stakeholder Perspectives" to group concerns and renames "Architecture Model" to "View Component."

### Cited Findings
- arc42 Section 7 (Deployment View) documents "the technical infrastructure used to execute your system, with infrastructure elements like geographical locations, environments, computers, processors, channels and net topologies," plus "the mapping of (software) building blocks to those infrastructure elements," and instructs documenting all relevant environments (e.g., development, test, production) when they differ, using infrastructure diagrams, motivation/justification, quality/performance features, and a two-level structure (Level 1 overview, Level 2 detailed internals); recommended notations include UML deployment diagrams or any notation able to show nodes and channels — [arc42 docs: 7 - Deployment view](https://docs.arc42.org/section-7/)
- arc42 Section 8 (Crosscutting Concepts) covers "practices, patterns, regulations or solution ideas" spanning multiple building blocks — technology choices, recurring patterns, development/deployment processes — forming "the basis for conceptual integrity (consistency, homogeneity)"; arc42 suggests it can be useful to define a "dynamic deployment concept" in Section 8 and cross-reference it from the Section 7 deployment view — [arc42 docs: 8 - Concepts](https://docs.arc42.org/section-8/); [arc42 docs: Tip 5-10 on crosscutting concepts](https://docs.arc42.org/tips/5-10/)
- The underlying infrastructure "can and will influence your system and/or some cross-cutting concepts," explicitly linking the deployment view (Section 7) to crosscutting concepts (Section 8) — [arc42 docs: 7 - Deployment view](https://docs.arc42.org/section-7/)
- ISO/IEC/IEEE 42010's conceptual model establishes that an **Architecture Viewpoint** frames one or more **Stakeholder Concerns**; each **Architecture View** has its own Architecture Viewpoint, and the Viewpoint is a specification for the View; each viewpoint definition links stakeholders and concerns to the notations/models used — [ISO/IEC/IEEE 42010 conceptual-model search synthesis, citing iso-architecture.org and trakviewpoints.sourceforge.io](https://trakviewpoints.sourceforge.io/what_is_an_architecture_viewpoint.html)
- The 2nd edition of ISO/IEC/IEEE 42010 introduces **Stakeholder Perspectives** as a means to group Concerns (and thereby organize Viewpoints that frame those concerns), and renames "Architecture Model" to **"View Component"** — [ISO/IEC/IEEE 42010 conceptual-model search synthesis](https://www.omgwiki.org/MBSE/lib/exe/fetch.php?media=mbse%3Aincose_mbse_iw_2022%3Aiw2022_iso_iec_ieee_42010_update.pdf)

### Inferences
- A tool supporting arc42-style deployment views needs to represent **multiple parallel environments** (dev/test/prod) as distinct, comparable diagram sets over the same logical architecture, plus a way to attach a **motivation/rationale text block** and **quality/performance annotations** to the deployment diagram itself (not just to individual shapes).
- Supporting arc42's Section 7 ↔ Section 8 cross-reference implies the tool should allow **named, reusable "concepts"** (e.g., a documented deployment/security/logging concept) that multiple diagrams or elements can link to, rather than concepts being redundantly re-described per diagram.
- To be ISO 42010-aligned, a tool would need to let a single underlying model be filtered into multiple **named views**, each view tagged with the **viewpoint** it conforms to and the **stakeholder concerns** it addresses — this is conceptually close to, and reinforces, the C4/Structurizr "one model, many views" pattern found above, suggesting this is a convergent, cross-framework requirement rather than one framework's quirk.
- ISO 42010's stakeholder/concern framing implies value in letting diagram elements or whole diagrams carry a **stakeholder-and-concern tag** (e.g., "addresses: Ops team / deployability concern") purely as metadata for documentation and review purposes.

### Gaps
- Both direct fetch attempts against `iso-architecture.org` failed with a connection error (`ECONNREFUSED`) in this session, so the ISO 42010 findings above rely on secondary-source search-result synthesis rather than a primary-source page read; the standard's exact defined terms (e.g., full definitions of "Architecture Description," "Architecture Rationale," "Correspondence") were not independently verified against the primary standard text or its official summary page in this pass.
- Did not find or verify a direct link between arc42's deployment view and ISO 42010 terminology (arc42 is influenced by but not formally mapped to 42010 in the sources retrieved) — treat any such mapping as an inference, not a cited fact.

## Non-functional requirements typically documented in infra design (availability/SLOs, RTO/RPO, DR strategy, scaling, network segmentation, data classification, observability, capacity)

### Takeaway
Across the frameworks researched, the clearest, most concretely sourced NFR-documentation requirements are AWS's RTO/RPO definitions and four named DR strategies (see AWS section above) and arc42's requirement to attach quality/performance features and motivation to the deployment view; other NFR categories (scaling, network segmentation, data classification, observability, capacity) are referenced by pillar names (e.g., Azure/GCP "Performance Efficiency," GCP "Reliability" mentioning horizontal scalability and observability) but were not independently deep-researched with primary-source detail in this pass.

### Cited Findings
- RTO and RPO are formally defined by AWS as: RTO = "the maximum acceptable delay between the interruption of service and restoration of service"; RPO = "the maximum acceptable amount of time since the last data recovery point," both "defined by the organization" (i.e., business-set, not technically fixed) — [AWS Reliability Pillar: DR objectives](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-objectives.html)
- RTO is explicitly distinguished from MTTR: "RTO is similar to MTTR... However MTTR is a mean value taken over several availability impacting events over a period of time, while RTO is a target, or maximum value allowed, for a single availability impacting event" — [AWS Reliability Pillar: DR objectives](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/disaster-recovery-dr-objectives.html)
- Google Cloud's Reliability pillar explicitly lists, as design considerations: "defining reliability based on user goals, setting realistic targets, building redundancy, horizontal scalability, observability, graceful degradation, and comprehensive failure testing and postmortems" — [Google Cloud Well-Architected Framework](https://docs.cloud.google.com/architecture/framework)
- Azure's Performance Efficiency pillar concern is "scalability, load testing"; Azure's Reliability pillar concern is "resiliency, availability, recovery"; Azure's Operational Excellence pillar concern is "holistic observability, DevOps practices" — [Microsoft Learn: Azure Well-Architected Framework pillars](https://learn.microsoft.com/en-us/azure/well-architected/pillars)
- arc42 Section 7 (Deployment View) explicitly calls for documenting "quality and performance features" of the infrastructure alongside the deployment structure itself, and for justifying ("motivation") why that deployment structure was chosen — [arc42 docs: 7 - Deployment view](https://docs.arc42.org/section-7/)

### Inferences
- Since RTO/RPO are explicitly "defined by the organization" per workload/resource (not derived automatically), a design tool needs **editable numeric/duration fields** attached at the workload level and potentially per data-store, rather than trying to infer them from the diagram topology.
- Because AWS frames DR-strategy choice as a direct function of RTO/RPO targets, a tool that lets users set RTO/RPO and then choose/tag a DR strategy (backup-restore / pilot-light / warm-standby / multi-site-active-active) per workload would let the diagram double as a lightweight DR-strategy declaration, consistent with how AWS's own whitepaper frames the decision.
- "Graceful degradation," "observability," and "horizontal scalability" (from GCP's Reliability pillar) suggest a tool could usefully support annotating scaling behavior (e.g., min/max replica counts, auto-scaling group boundaries) directly on resource elements, reusing the same "replica count" concept implied by the AWS multi-AZ redundancy modeling need noted earlier.

### Gaps
- Network segmentation, data classification, and capacity planning were not directly researched against primary framework sources in this pass (time/tool-call budget was spent on AWS DR strategy, RTO/RPO, and the multi-framework pillar/viewpoint comparison, which were higher priority per the assignment's explicit key questions). A follow-up pass should specifically fetch AWS's Security pillar (data classification, network segmentation via security groups/NACLs) and Google Cloud's / Azure's Security pillar detail pages, which were only summarized at the pillar-name level here.
- No dedicated primary source was found in this pass for a formal, cross-framework definition of "SLO" as distinct from availability targets (the term did not appear directly in the fetched AWS/Azure/GCP content; AWS's fetched pages used "availability" and "RTO/RPO" rather than "SLO" terminology).

## Architecture Decision Records (ADRs) and linking decisions to diagram elements

### Takeaway
ADRs document a single, justified, architecturally-significant decision (context, decision, consequences) and exist as a versioned, numbered log; multiple templates exist (Nygard's minimal format, Tyree & Akerman's more detailed format, MADR, arc42-style, etc.), but no source retrieved in this pass described a standardized, tool-native mechanism for linking an ADR to a specific diagram element — this appears to be a general architecture-documentation practice gap that a diagramming tool could fill.

### Cited Findings
- An Architectural Decision (AD) is "a justified design choice that addresses a functional or non-functional requirement that is architecturally significant," and an ADR captures a single such decision and its justification — [adr.github.io search-result synthesis](https://adr.github.io/); note: direct WebFetch of adr.github.io failed in-session (connection error), so this is sourced from the search-snippet summary, not a full page read
- Common ADR templates include: **Michael Nygard's** format (simple, widely used), **Jeff Tyree & Art Akerman's** format (more detailed, for organizations needing fuller stakeholder communication), **MADR** (Markdown Any Decision Records, with a simple and an "options + pros/cons" extended version), an **arc42-style** ADR template, the **Alexandrian pattern** format, a business-case-oriented template (with cost/SWOT), and a **Planguage** template emphasizing quality attributes — [GitHub: joelparkerhenderson/architecture-decision-record](https://github.com/joelparkerhenderson/architecture-decision-record)
- Typical ADR sections across templates: **Title** (present-tense imperative phrase, e.g., "choose-database"), **Status** (lifecycle stage), **Context** (situation/business priorities), **Decision** (the choice made), **Consequences** (effects/outcomes/follow-ups); numbering/organization is conventionally done via sequential file-name numbering plus a descriptive slug, and one ADR's consequences can note that it "triggers the need for more ADRs" (implying a lightweight dependency chain rather than a formal cross-reference schema) — [GitHub: joelparkerhenderson/architecture-decision-record](https://github.com/joelparkerhenderson/architecture-decision-record)

### Inferences
- Since ADRs are decision-per-file, sequentially numbered, and Markdown-based in common practice, a diagramming tool could support **attaching an ADR reference/ID (or a link/URL to an ADR file) as metadata on a diagram element or connector** (e.g., "this cross-region replication link implements ADR-0007: choose pilot-light DR strategy") — this would be a straightforward metadata field rather than requiring the tool to host ADR content itself.
- Because ADR "Consequences" sections informally trigger follow-on ADRs, a tool that supports **linked/threaded metadata references** (this element → ADR ID → related ADR IDs) would better mirror real practice than a single flat text field.
- No evidence was found of an existing *standard* schema for diagram-to-ADR linking (e.g., no C4/arc42/ISO-42010 source retrieved defines this explicitly), so this is a design opportunity/gap rather than a documented requirement — a tool implementing it would be adding value beyond what any single framework mandates, not conforming to an existing cross-framework standard.
