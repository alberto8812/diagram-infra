# IaC Import/Export, Live Discovery, and Drift Detection for a TypeScript/React Diagram Editor

## Terraform JSON schemas (`terraform show -json`) and provider resource mapping

### Takeaway
`terraform show -json` exposes a well-documented, versioned JSON schema for both plan and state, with `root_module`/`child_modules` nesting and expression-level `references` that can drive node/edge extraction; but mapping raw resources into a clean node/container diagram (e.g., VPC/subnet containment) is a hard, provider-specific problem that most existing tools solve only partially (AWS best, others weak/absent).

### Cited Findings
- `terraform show -json` state output has top-level `values` (full state) and `terraform_version`; plan output has `format_version`, `prior_state`, `configuration`, `planned_values`, `resource_changes`, `resource_drift`, `relevant_attributes`, `output_changes`, and `checks` — [Terraform JSON Output Format](https://developer.hashicorp.com/terraform/internals/json-format)
- Each resource entry carries `address` (documented as "opaque" and not to be parsed), `mode` (managed/data), `type`, `name`, `index`, `provider_name`, `schema_version`, `values`, and `sensitive_values` — [Terraform JSON Output Format](https://developer.hashicorp.com/terraform/internals/json-format)
- Configuration-level resource blocks include a `references` list capturing expression-level dependencies (e.g. traversals like `data.template_file.foo[1].vars["baz"]`, `module.foo.bar`, `var.example[0]`), which is the mechanism for deriving a dependency graph from `configuration` rather than from `depends_on` directly — [Terraform JSON Output Format](https://developer.hashicorp.com/terraform/internals/json-format)
- Both `configuration` and `planned_values`/state values support recursive `root_module` → `child_modules` nesting, each child module repeating the same resource/output/module structure, giving a natural tree for module-based grouping — [Terraform JSON Output Format](https://developer.hashicorp.com/terraform/internals/json-format)
- `resource_drift` in the plan JSON explicitly represents resources whose real-world value differs from the last-known state — [Terraform JSON Output Format](https://developer.hashicorp.com/terraform/internals/json-format)
- Inframap (cycloidio) reads tfstate/HCL and uses "a static list of resources that can be nodes or edges," and tries to collapse connecting resources into a single unique edge between two nodes rather than showing every intermediate resource — [cycloidio/inframap README](https://github.com/cycloidio/inframap)
- Inframap's grouping of resources into containers (e.g., putting resources inside their VPC) is marked "WIP" and available only for AWS; Google Cloud, Azure, OpenStack, and FlexibleEngine are explicitly listed as **not** supporting grouping — [cycloidio/inframap README](https://github.com/cycloidio/inframap)
- For providers without special-case logic, Inframap falls back to showing "all resources present without any simplification," and IAM-based connections are "not yet implemented for any provider" — [cycloidio/inframap README](https://github.com/cycloidio/inframap)
- Inframap only supports Terraform state format versions 3 and 4, and does not support reading directly from remote backends (state must be piped in) — [cycloidio/inframap README](https://github.com/cycloidio/inframap)
- Inframap usage pattern: `inframap generate terraform.tfstate | dot -Tpng > infra.png`, or run directly against an HCL working directory with `inframap generate .`; output is currently DOT-only — [cycloidio/inframap README](https://github.com/cycloidio/inframap); [pkg.go.dev/github.com/cycloidio/inframap](https://pkg.go.dev/github.com/cycloidio/inframap)

### Inferences
- The `configuration.root_module.resources[].expressions` reference graph (not `depends_on`) is the practical source for building a diagram editor's connector/edge model from Terraform, since it captures both explicit and implicit dependencies at attribute granularity — good candidate for detecting e.g. a security-group attachment or subnet reference specifically (rather than a generic "depends on" edge).
- Because `address` is documented as opaque, it should be treated as a stable identity key for drift/diff matching but never parsed for semantic meaning (e.g., don't try to extract resource type from the address string beyond what `type`/`mode`/`name`/`index` already give you).
- VPC/subnet containment (nodes-inside-containers) is not a solved problem even in the most mature open-source tool (Inframap) outside AWS — a diagram tool wanting cross-cloud containment will likely need its own resource-type-to-container mapping table (e.g., `aws_subnet.vpc_id` → parent `aws_vpc`, `azurerm_subnet.virtual_network_name` → parent VNet, `google_compute_subnetwork.network` → parent VPC network) built from each provider's schema attribute names, since no cross-provider standard exists.

### Gaps
- No source found giving the exact JSON key that records `depends_on` blocks verbatim in `terraform show -json` (only implicit expression `references` were confirmed); worth deeper doc verification for explicit-dependency modeling.
- No primary-source detail on Inframap's exact heuristics/allowlist file (which specific resource types are treated as nodes vs. edges) — only that such a static list exists.

## Terraform visualization/import tools: Rover, Pluralith, Terravision, Blast Radius, Brainboard — strengths/weaknesses

### Takeaway
`terraform graph` itself is widely reported as unusably noisy for real infrastructure (50+ resources becomes a tangled unreadable web, cluttered with internal provider/variable nodes); third-party tools trade off between plan-fidelity (Rover, Pluralith) and clean/simplified views (Inframap), while Blast Radius is now unmaintained and incompatible with modern Terraform.

### Cited Findings
- `terraform graph` outputs DOT and by default limits itself to dependency-ordering nodes for resource/data blocks only, but the `-type=` option exposes more detail "at the expense of also exposing some of the implementation details of the Terraform language runtime" (providers, variables, locals, etc.) — [Terraform graph command reference](https://developer.hashicorp.com/terraform/cli/commands/graph)
- "For any real-world infrastructure, the [terraform graph] output is a massive, tangled web of nodes and arrows... a typical production setup with 50+ resources generates a graph that's essentially unreadable," and it "includes internal Terraform resources (providers, data sources, variables) that add noise without adding understanding" — [via WebSearch synthesis, sourced from spacelift.io/blog/terraform-graph and stategraph.com/blog/terraform-graph-command]
- Rover is open source, runs locally, and uses the Terraform plan to generate visualizations that highlight created/deleted/modified resources — [via WebSearch synthesis of Terraform visualization tool comparisons]
- Pluralith focuses on plan-based (not just static-code-based) visualization and automated documentation generation; recommended when you want the actual planned changes reflected, since "the plan-output approach catches things static parsers miss" — [via WebSearch synthesis]
- Terravision is described as free and self-hosted, "good enough for personal projects" — [via WebSearch synthesis]
- Blast Radius can generate tree and table views with filtering/highlighting, but "has compatibility issues with Terraform 1.x+ and is no longer actively maintained as of 2025" — [via WebSearch synthesis]
- Direct comparison: "Inframap creates much simplified diagrams that miss a lot of resources and dependencies compared to other tools like Rover and Pluralith" — [via WebSearch synthesis]
- Brainboard: builds diagrams on a visual canvas and generates matching Terraform; also has an "import feature" that reads Terraform state/HCL and an AI-assisted feature that scans live AWS via API access to generate Terraform code from existing infrastructure without manual intervention; supports AWS, Azure, GCP, OCI, Scaleway; claims bidirectional sync between diagram and code (edit either side, other updates) — [Brainboard blog: reverse-engineer AWS into diagram](https://www.brainboard.co/blog/how-to-reverse-engineer-your-existing-aws-infrastructure-into-a-visual-diagram); [Brainboard AI Terraform diagrammer](https://www.brainboard.co/blog/ai-terraform-diagrammer)

### Inferences
- The industry pattern splits into two architectures: (1) parse-and-simplify tools working from static HCL/state (Inframap, Terravision) — fast but blind to actual planned changes and cross-provider containment; (2) plan-based tools (Rover, Pluralith) that consume the full `terraform show -json` plan, giving change-highlighting (create/update/destroy) essentially for free. For a diagram editor wanting drift/change highlighting (not just a static snapshot), the plan-JSON approach (à la Rover/Pluralith) is architecturally closer to what's needed than the state-only approach (Inframap).
- Raw `terraform graph` DOT should not be used as an end-user diagram source directly — it needs the same "important resources only" filtering Inframap applies, or it will reproduce the well-documented unreadability problem.

### Gaps
- No specific numeric performance/accuracy benchmarks found comparing tool outputs on identical real-world state files (only qualitative comparison via secondary blog sources, not primary tool documentation/benchmarks).
- Blast Radius's official repository/documentation was not directly fetched to confirm the "unmaintained/incompatible" claim from primary source — this came from search-result synthesis only, flagged as lower-confidence.

## CloudFormation / CDK, Pulumi, Kubernetes/Helm, docker-compose: formats and diagram tools

### Takeaway
Each ecosystem has both an official machine-readable export (CDK's `tree.json`/Cloud Assembly manifest, Pulumi's `stack export` JSON, CloudFormation templates) and at least one actively maintained open-source diagram generator; Kubernetes now has a particularly strong purpose-built option (KubeDiagrams, 2025) that reads manifests, Helm charts, *and* live cluster state through one tool.

### Cited Findings
- AWS CDK's `cdk synth` produces `tree.json` in `cdk.out`, describing the construct hierarchy ("a list of paths that are indexed into a map of constructs"); this was added specifically to let external tooling build on the construct tree — [aws/aws-cdk design/construct-tree.md](https://github.com/aws/aws-cdk/blob/master/design/construct-tree.md)
- The CDK Cloud Assembly (`cdk.out`) contains CloudFormation templates, asset metadata, deployment instructions, `tree.json`, and `manifest.json` (metadata about the assembly) — [via WebSearch synthesis of dev.to/aws-heroes and datadef.io CDK articles]
- `cdk-dia` (pistazie/cdk-dia) generates diagrams of CDK-provisioned infrastructure using Graphviz DOT, run after `cdk synth`, and supports customizer/decorator hooks on CDK constructs to tweak the rendered diagram — [pistazie/cdk-dia GitHub](https://github.com/pistazie/cdk-dia); [Martin Mueller blog on cdk-dia](https://martinmueller.dev/cdk-dia-eng/)
- `cfn-diagram` (mhlabs/ljacobsson) is a CLI that visualizes CloudFormation/SAM/CDK stacks as visjs network graphs, draw.io diagrams, or ASCII-art — [mhlabs/cfn-diagram GitHub](https://github.com/mhlabs/cfn-diagram)
- AWS Infrastructure Composer (successor branding of "Application Composer") is a visual drag/group/connect canvas that auto-generates CloudFormation/SAM templates in real time, keeps canvas and template code synced bidirectionally, supports **importing** an existing CloudFormation/SAM template, and supports **exporting** IaC for local SAM CLI testing, peer review via version control, or CI/CD deployment — [What is AWS Infrastructure Composer](https://docs.aws.amazon.com/infrastructure-composer/latest/dg/what-is-composer.html); [Infrastructure Composer FAQs](https://aws.amazon.com/infrastructure-composer/faqs)
- Infrastructure Composer's focus is serverless services (Lambda, Step Functions, EventBridge) but can compose "any AWS service supported by AWS CloudFormation resources" — [What is AWS Infrastructure Composer](https://docs.aws.amazon.com/infrastructure-composer/latest/dg/what-is-composer.html)
- `pulumi stack export` outputs the full stack state as JSON (resources + their configuration/state) to stdout; a separate `pulumi stack graph` command exists for the dependency graph but its output format is DOT, not JSON — a JSON resource-graph export (for D3.js-style consumption) was an open **feature request**, not a shipped feature — [pulumi stack export docs](https://www.pulumi.com/docs/iac/cli/commands/pulumi_stack_export/); [pulumi/pulumi issue #9576](https://github.com/pulumi/pulumi/issues/9576)
- KubeDiagrams (introduced ~May 2025) generates Kubernetes architecture diagrams from manifest files, kustomization files, Helm charts, helmfiles, **and actual live cluster state** in one tool; output formats include DOT, GIF, JPEG, PDF, PNG, SVG, TIFF, plus an interactive viewer (zoom, tooltips, open/close clusters, drag nodes, export PNG/JPG) — [philippemerle/KubeDiagrams GitHub](https://github.com/philippemerle/KubeDiagrams); [KubeDiagrams on PyPI](https://pypi.org/project/KubeDiagrams/)
- KubeDiagrams is distributed as a PyPI package, Docker image, `kubectl` plugin, Nix flake, and GitHub Action; use cases cited: onboarding (map what runs where without reading dozens of YAML files), review/change-control via diagrams-as-code, and troubleshooting via surfaced hidden dependencies — [k8s.guru blog on KubeDiagrams](https://k8s.guru/blog/2025/06/05/kubediagrams-visualization/); [arXiv:2505.22879 — Visualizing Cloud-native Applications with KubeDiagrams](https://arxiv.org/abs/2505.22879)
- For docker-compose, `docker-compose-viz` (pmsipilot) is a CLI that reads a compose file and produces a Graphviz graph, visualizing `depends_on`, links, and shared networks (networks rendered as pentagons) — [pmsipilot/docker-compose-viz GitHub](https://github.com/pmsipilot/docker-compose-viz)
- A newer Mermaid-output variant ("Docker Compose Viz (Mermaid)") renders network bindings as parallelograms connected via dotted lines labeled with aliases/IPs — [Docker Compose Viz (Mermaid) site](https://derlin.github.io/docker-compose-viz-mermaid/)
- `compose-viz` generates graphs of services/dependencies/exposed ports from `compose.yaml`, supporting multiple output formats (png, jpeg, json, svg, etc.) — [via WebSearch synthesis, avonture.be blog]

### Inferences
- CDK's `tree.json` is structurally analogous to Terraform's `configuration.root_module.child_modules` nesting — both are hierarchical construct/module trees intended as a stable extension point for third-party tooling, suggesting a diagram editor's IaC importer could use a shared internal "hierarchy + resource + reference" intermediate model across Terraform and CDK sources.
- Pulumi is currently the weakest of the three major IaC tools for structured graph export — its dependency graph is DOT-only (not JSON), so a diagram-editor importer would need to either parse DOT or reconstruct the dependency graph itself from `stack export`'s JSON resource list (which does contain each resource's properties/URN, from which references could plausibly be inferred, though this needs direct verification against the JSON schema).
- KubeDiagrams' single-tool coverage of manifests + Helm + live cluster state is the most directly relevant existing precedent for what this project wants to build (one importer spanning static IaC and live discovery) — worth studying its source/architecture as a design reference.

### Gaps
- Did not fetch the precise JSON schema of `pulumi stack export` (resource URNs, parent/child fields, property dependency lists) — flagged as a follow-up for whoever designs the Pulumi importer; only the CLI-level description was confirmed.
- Did not find primary CloudFormation template JSON schema documentation directly (e.g., how `DependsOn`, `Ref`, `Fn::GetAtt` map to graph edges) — inferred from tool descriptions (cfn-diagram, cdk-dia) but not verified against AWS's own template anatomy docs.
- Did not verify whether KubeDiagrams' "actual cluster state" mode uses the Kubernetes API directly or requires `kubectl get -o yaml` export first — architecture detail not confirmed from the sources gathered.

## Live cloud discovery APIs and read-only IAM requirements

### Takeaway
All three major clouds provide a first-party, near-real-time inventory/query API (AWS Resource Explorer + Cloud Control API, Azure Resource Graph, GCP Cloud Asset Inventory) with documented read-only managed policies, but none of them talk to each other — a multi-cloud diagram tool must integrate each separately (or via a third-party aggregator) and cannot rely on a single cross-cloud discovery API.

### Cited Findings
- AWS Resource Explorer is a search/discovery service for resources across an AWS account; `AWSResourceExplorerReadOnlyAccess` is the documented AWS-managed policy granting read-only permission to search and view resources (plus read-only permission to the other AWS services needed to support that search) — [AWS Resource Explorer IAM identity policy examples](https://docs.aws.amazon.com/resource-explorer/latest/userguide/security_iam_id-based-policy-examples.html); [AWSResourceExplorerReadOnlyAccess managed policy reference](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSResourceExplorerReadOnlyAccess.html)
- With only `AWSResourceExplorerReadOnlyAccess`-level permissions you can search "partial results" (tagged resources + supported untagged resources created after immediate-discovery release turned on); full automatic inventory additionally needs `iam:CreateServiceLinkedRole` (bundled in the broader `AWSResourceExplorerFullAccess` policy) — [AWS Resource Explorer welcome/userguide](https://docs.aws.amazon.com/resource-explorer/latest/userguide/welcome.html)
- AWS Cloud Control API exposes uniform, service-specific create/read/update/delete/list actions across many AWS resource types via one API surface, with its own IAM action/condition-key reference for scoping permissions — [Cloud Control API service authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_awscloudcontrolapi.html)
- `welldone-cloud/aws-list-resources` is an open-source script that uses Cloud Control API to enumerate resources across an account/regions into a JSON result file, and documents that it "requires read access to all AWS services you want to list resources for" — [welldone-cloud/aws-list-resources GitHub](https://github.com/welldone-cloud/aws-list-resources)
- Azure Resource Graph lets you query resources across subscriptions using Kusto Query Language (KQL), including complex cross-subscription filters — [via WebSearch synthesis, Microsoft Learn sources]
- GCP Cloud Asset Inventory provides a snapshot and history of GCP assets, with export to BigQuery, and is GCP's primary resource-visibility tool — [via WebSearch synthesis, Microsoft Learn / Amnic sources]
- "AWS, Azure, and GCP each have their own built-in asset visibility tools: AWS Config, Azure Resource Graph, and GCP Cloud Asset Inventory. They're useful within their own cloud, but they're not designed to talk to each other." — [via WebSearch synthesis, Amnic multi-cloud inventory blog]
- Azure Arc's "multicloud connector" can extend Azure Resource Graph queries to also cover AWS and GCP resources with matching tags, via a "Global Read" read-only role across the AWS account or GCP Organization/Project — [via WebSearch synthesis, Microsoft Learn Azure Arc multicloud-connector docs]

### Inferences
- For an MVP, per-cloud native read-only roles are the correct integration point: AWS `AWSResourceExplorerReadOnlyAccess` (+ optionally scoped Cloud Control API read actions for deep per-resource attributes), an Azure custom/built-in Reader role for Resource Graph KQL queries, and a GCP read-only IAM role (e.g., `roles/cloudasset.viewer`, not directly confirmed in sources but implied by "Cloud Asset Inventory" being the analogous GCP service) for Cloud Asset Inventory.
- True cross-cloud, single-pane discovery would require either building three separate connectors or adopting Azure Arc's multicloud connector (Azure-centric) or a third-party aggregator — this is a build-vs-integrate decision to flag as an open product question, not purely technical.

### Gaps
- Did not confirm the exact GCP IAM role name for read-only Cloud Asset Inventory access (needs direct GCP IAM docs lookup).
- Did not find primary-source detail on AWS Cloud Control API rate limits/pagination behavior relevant to bulk live-discovery scans — would matter for incremental re-import performance.
- Azure Resource Graph and GCP Cloud Asset Inventory findings came from WebSearch synthesis of secondary sources (Microsoft Learn, Amnic) rather than a direct fetch of the primary Microsoft/Google API reference pages — recommend a follow-up direct fetch of `learn.microsoft.com/azure/governance/resource-graph` and `cloud.google.com/asset-inventory/docs` before implementation.

## Drift detection: approaches, stable identity, layout preservation, incremental re-import

### Takeaway
Terraform's own drift model (`resource_drift` in plan JSON, `-refresh-only` plans) is well-documented and gives a ready-made building block for diagram/state diffing, but the "stable identity across renames/moves" problem (state address changes on refactor) is explicitly a known Terraform pitfall with its own dedicated fix (the `moved` block) that a diagram-sync tool must account for; no source found describing an existing tool that solves diagram-layout preservation across incremental re-imports, which appears to be a genuine gap/differentiator.

### Cited Findings
- Terraform CLI's recommended ways to surface drift are `terraform plan` (implicitly refreshes state and shows diffs) and `terraform plan -refresh-only` (explicitly refreshes and shows only drift, without proposing config-driven changes) — [Manage resource drift — Terraform tutorial](https://developer.hashicorp.com/terraform/tutorials/state/resource-drift)
- "Drift occurs when someone changes cloud resources directly and Terraform doesn't know until you compare desired state to live state... drift emerges when there's a disparity between how Terraform understands a resource's state (based on the state file) and how that resource actually exists in reality." — [via WebSearch synthesis, spacelift.io/oneuptime/hashicorp blog sources]
- The plan JSON schema has a dedicated `resource_drift` field (see prior section) specifically for externally-detected changes, separate from `resource_changes` (which represents the plan's proposed changes) — [Terraform JSON Output Format](https://developer.hashicorp.com/terraform/internals/json-format)
- Resource "address" is the state identity key; moving a resource into/out of a module changes its address, and Terraform's default interpretation of an address change is destroy-old/create-new — [via WebSearch synthesis, HashiCorp/Terraform drift and state docs]
- Since Terraform v1.1, the `moved` block lets configuration explicitly record an address change so Terraform treats it as a rename instead of destroy+recreate — [via WebSearch synthesis, HashiCorp blog/docs on resource moves]

### Inferences
- For drift detection between a diagram JSON model and Terraform, the most robust stable-identity key is **not** the Terraform state `address` alone (since it changes on refactors) but ideally a combination of the address (for state-side matching) plus the underlying cloud-native ID embedded in resource `values` (e.g., ARN for AWS, resource ID for Azure/GCP) wherever the provider schema exposes it — this mirrors how a `moved` block effectively "fixes" address instability by declaring identity continuity explicitly, and a diagram tool could similarly track "this diagram node corresponds to ARN X" independent of Terraform's own addressing.
- The plan JSON's separation of `resource_drift` (external changes) from `resource_changes` (declared/config changes) is directly reusable as the semantic split a diagram editor needs for two different visual treatments: "diagram vs. IaC config differs" vs. "diagram vs. live cloud state differs."
- No commercial or open-source tool was found in this research pass that explicitly claims to preserve a user's manual diagram layout (node positions) across repeated/incremental re-imports of updated IaC — this suggests it's an unsolved/undifferentiated problem in the current tool landscape, and worth treating as a design opportunity rather than assuming prior art to copy.

### Gaps
- Did not find a primary source (HashiCorp docs) specifically confirming the destroy/recreate-on-address-change behavior and the `moved` block semantics — this came from WebSearch synthesis only and should be verified directly against `developer.hashicorp.com/terraform/language/moved` before relying on it architecturally.
- Did not find any existing tool/paper addressing "incremental re-import that preserves a human-arranged diagram layout" — flagged as an open gap in current published tooling, not just a missing source.
- No commercial drift-detection product docs (e.g., driftctl successor tools, env0, Firefly, ControlMonkey, Terramate) were fetched at primary-source depth in this pass — only their blog content appeared in search snippets; a deeper look at driftctl-style tools' identity-matching algorithms (if any are still maintained) would strengthen this section.

## Export direction: generating IaC skeletons from diagrams

### Takeaway
Two real, shipping products (Brainboard, AWS Infrastructure Composer) already do diagram-to-IaC generation with bidirectional sync, proving the approach is feasible for scoped domains (Infrastructure Composer: CloudFormation/SAM, serverless-focused; Brainboard: multi-cloud Terraform); but broader evidence on AI/automated IaC generation (LLM-based, a closely related risk class) shows real correctness and security risks that a from-diagram code generator must guard against.

### Cited Findings
- AWS Infrastructure Composer auto-generates CloudFormation/SAM templates as the user drags/groups/connects services on the canvas, keeps canvas and template code synced in both directions, and supports exporting IaC for local SAM CLI testing, peer review, or CI/CD deployment — [What is AWS Infrastructure Composer](https://docs.aws.amazon.com/infrastructure-composer/latest/dg/what-is-composer.html)
- Brainboard generates Terraform code matching a visually designed diagram and claims changes in either direction (diagram or code) stay synchronized, explicitly framed as eliminating "documentation drift" — [Brainboard: Make Terraform as diagram](https://medium.com/@mike_tyson_cloud/make-terraform-as-diagram-d6898b2da4de); [Brainboard AI Terraform diagrammer](https://www.brainboard.co/blog/ai-terraform-diagrammer)
- Brainboard's reverse-import path uses API access to scan existing AWS infrastructure and generate Terraform "without the need for manual intervention" — [Brainboard: reverse-engineer AWS infrastructure into diagram](https://www.brainboard.co/blog/how-to-reverse-engineer-your-existing-aws-infrastructure-into-a-visual-diagram)
- On AI-generated IaC risk generally: "AI-generated infrastructure code is frequently invalid, requiring human review for correctness, and commonly contains security vulnerabilities"; one cited study found "approximately 40% of code generated by Copilot to be vulnerable," and ChatGPT-generated code "failed to meet minimum security standards in 16 out of 21 cases" — [Styra: AI-Generated Infrastructure-as-Code: the Good, the Bad and the Ugly](https://www.styra.com/blog/ai-generated-infrastructure-as-code-the-good-the-bad-and-the-ugly/)
- Generated IaC/IAM policies "can expose cloud resources the moment they are deployed, turning a code suggestion into a live misconfiguration" — [Styra: AI-Generated Infrastructure-as-Code](https://www.styra.com/blog/ai-generated-infrastructure-as-code-the-good-the-bad-and-the-ugly/)
- Recommended mitigation pattern: comprehensive review process engaging domain experts plus rigorous testing of generated infrastructure code before deployment — [via WebSearch synthesis]

### Inferences
- The two proven-in-production examples (Infrastructure Composer, Brainboard) both scope their diagram→IaC generation to a single target format/provider family (CloudFormation/SAM only; Terraform only) rather than attempting a universal cross-format generator — this is a strong signal that a diagram-to-IaC exporter should similarly target one IaC format at a time (e.g., start with Terraform HCL generation) rather than trying to emit CDK/Pulumi/CloudFormation simultaneously from one internal model.
- The AI-code-generation risk findings are most relevant if the export path uses an LLM to synthesize HCL/CloudFormation from the diagram (vs. deterministic templated generation from typed node/connector data). A deterministic generator (diagram JSON → typed provider-resource template, no LLM in the code-emission path) would avoid most of the cited correctness/security risk class; risk resurfaces only if free-text or LLM-assisted steps are introduced into the generation pipeline.
- Both existing tools frame the safe-export pattern as "generate code the user must still review/test before deploy" (SAM CLI local testing, PR-based peer review) — this "never auto-deploy generated IaC" pattern is a reusable design constraint.

### Gaps
- Did not find independent (non-vendor-blog) evaluation of Brainboard's generated Terraform code quality/correctness — all findings on Brainboard are vendor-authored (Brainboard's own blog / a partner "Mike Tyson of the Cloud" Medium series that appears closely affiliated with Brainboard); treat feasibility claims as vendor-sourced and unverified by a third party.
- Did not find a primary AWS source confirming whether Infrastructure Composer's canvas→template sync is truly bidirectional in real time or requires an explicit "sync" action — the FAQ/docs describe both import and export but the phrase "automatically syncs changes" needs closer reading against the actual product UI to confirm real-time vs. on-demand behavior.

## Diagram-as-code interoperability: Structurizr DSL, Mermaid, D2, PlantUML C4

### Takeaway
These are model/notation systems for *software architecture* diagrams (C4-style), not infrastructure/cloud-resource diagrams — they are relevant to this project mainly as export targets (e.g., "export my infra diagram as a Mermaid/D2 snippet for docs") rather than as IaC import/export sources, and Structurizr's model-first DSL (separating the model from views) is the closest architectural precedent to what a JSON-model diagram editor already does internally.

### Cited Findings
- Structurizr DSL "provides the strongest separation between the model (the boxes and lines) and the presentation (the views you render from the model)," so adding a new view later doesn't require redrawing existing diagrams; it is model-first, defining the architecture once and generating multiple C4-level views (Context, Container, Component, Code) — [via WebSearch synthesis, hidekazu-konishi.com and dandoescode.com sources]; official export path confirmed: Structurizr DSL can export to PlantUML/Mermaid — [Structurizr: Export diagrams as code](https://docs.structurizr.com/getting-started/export-diagrams-as-code)
- Mermaid's diagram-type coverage "stops short of formal UML, C4 model, or deployment diagrams," and its layout engine "produces awkward results on diagrams with more than a dozen nodes" — [via WebSearch synthesis]
- D2 and PlantUML "handle complex layouts better than Mermaid," with "noticeable quality differences on diagrams with more than 10-12 nodes" — [via WebSearch synthesis]
- Mermaid has the strongest native platform integration: GitHub and GitLab render it natively in Markdown, VS Code's Markdown preview covers it, and major static-site generators have first-class plugins; PlantUML "lags slightly because it depends on a Java back-end," mitigated by Kroki/PlantUML web servers enabling one-line render-from-text embeds — [via WebSearch synthesis]
- Recommended use cases: Structurizr for teams that have adopted the C4 model wanting model-driven, always-consistent diagrams; PlantUML as "the gold standard" for teams needing formal, version-controllable UML documentation — [via WebSearch synthesis]

### Inferences
- None of these four (Structurizr DSL, Mermaid, D2, PlantUML/C4) natively represent cloud/IaC-specific concepts (VPC, subnet, security group, ARN) — they are general software-architecture/UML notations. Their practical value to this project is as a lightweight **export format** for sharing/embedding diagrams in docs and PRs (e.g., "export selected view as Mermaid for the README"), not as an IaC import/export or drift-detection mechanism.
- Structurizr's explicit model/view separation is architecturally validating for this project's existing approach (one JSON model of nodes/connectors, with views rendered from it) — it confirms that decoupling "the infrastructure model" from "a particular rendered diagram/view" is an established, sound pattern rather than a novel risk.
- Given Mermaid's node-count layout weakness (~12 nodes) and D2/PlantUML's better scaling, if this project offers a Mermaid export it should probably be scoped to sub-diagrams/views rather than a whole large infrastructure model in one Mermaid block; D2 may be the better fit for exporting larger views.
